# Global working rules (Steve's projects)

These are my defaults across all my projects. A project's own `CLAUDE.md` overrides
anything here. "Remember this for all my projects" means update **this** file.

Current projects following these rules: `stevewang.me`, `fuel-tracker-app`,
`shared-bill-app`, `stackvitals`, `Ordering-APP` (purchasing workflow tools).
`project-status-hub` is a **deploy-only mirror of `stackvitals`** — never do work or
commit there; it only receives syncs of `main` from the stackvitals repo.
Contact/author email for all projects: **contact@stevewang.me**.

## Git branch flow

- Everyday work commits directly to the local **`dev`** branch. Keep `main` matching
  `origin/main`.
- **Fetch before committing — always.** Before making any commit in a repo, `git fetch origin`
  and fast-forward the local branch from its remote (`git merge --ff-only origin/<branch>`).
  Never commit on a branch that is behind its remote. If it happens anyway: undo the commit
  (`git reset --soft`), fast-forward, then re-apply the commit on top.
- Use a short-lived branch **only when a change is big or risky** — roughly, more than a
  few steps of work *and* with real potential to break the working project, so it's better
  merged only once completely finished. Not every new feature/refactor needs one; small,
  safe changes go straight on `dev`. Name the branch by the kind of work — `feat/<name>`,
  `fix/<name>`, `refactor/<name>`, etc. — cut from `dev`. (No need to ask before opening a
  branch — just keep it to large/risky work.)
- **Every branch lands via a GitHub PR, squash-merged** with a single Conventional Commit
  title — this applies to **both** `feat/*` → `dev` **and** the `dev` → `main` release.
  Never create merge commits. (Small changes committed directly to `dev` need no PR.)
- **Releasing is manual and I do it myself.** The **squash-merge `dev` → `main` PR** is the
  production deploy — AWS Amplify builds from `main` on push. **After each release, reset
  `dev` to `main`** (not a merge) so `dev` stays current. Repos with a `release:tag` script
  use it for the tag + reset; repos without one use the **`/release` skill**.
- **Never push.** Pushing `main` is what triggers the production deploy. Never push, create
  a remote branch, or publish anything unless I explicitly ask.

## Commits

- **One-line Conventional Commits, subject only** (`feat:`, `fix:`, `refactor:`, `chore:`,
  `build:`, `docs:`). No body/description paragraph unless I ask. When squash-merging
  via `gh pr merge --squash`, always pass `--body ""` to strip the auto-generated commit
  body that GitHub appends (list of squashed commits / PR description).
- **No AI mentions anywhere in git history** — no co-author trailers, no "generated by",
  nothing. Write like a human maintainer.
- Commit finished work without being asked; split unrelated work into separate commits.
- A **new commit** for a new task; **amend** the previous commit only when fixing my own
  earlier work from this session (unless I say otherwise). Don't revert unrelated work.
- Branch names are meaningful and descriptive, never auto-generated strings.

## Reuse over duplication

- Reuse the shared core/logic — never fork or reimplement it for a second surface.
- Don't add a duplicate feature, UI surface, control, or helper when an existing owner
  already covers the need. Improve the existing owner instead, unless I confirm a second
  surface.

## Docs & plans

- Most projects keep an authoritative plan doc (e.g. `docs/PROJECT_PLAN.md`,
  `docs/*_HUB_PLAN.md`). **Read it before changing code**, and update it in the **same
  change** when scope, positioning, decisions, guardrails, or deployment assumptions shift.
- `docs/` is **not strictly Git-ignored** — some docs are tracked, some are private, and it
  varies by project. Don't commit a doc that's Git-ignored, and never copy private details
  (employer names, internal URLs, private workflow specifics) into committed files. But I
  may explicitly ask you to include a particular doc — do it when I say so.
- Treat anything committed to a public repo as published.

## Security

- **Never commit** credentials, API keys, AWS/Supabase secrets, service-role keys, `.env`,
  or config files holding real resource IDs. Keep secrets out of any frontend bundle.
- **Never read the literal value of a secret, and never send one back through any API call.**
  This covers `.env` files, service-role/API keys, tokens, passwords — anything credential-
  shaped. Only the **key/variable name** may be read or referenced (e.g. note that
  `AWS_ACCESS_KEY_ID` is set, don't `cat`/`Read` the file to see what it equals). When a
  value is actually needed to run something, let the shell/tool pull it from the environment
  by name so it's consumed without ever landing in context or a response — never paste a
  literal secret value into a tool call, file, or message. Reason: anything that enters
  context can be sent to a model API or end up logged/persisted; the name alone carries no
  risk.
- If a secret value has already been read into context in a session (mine or a subagent's),
  treat that as done and unrecoverable for that transmission, but immediately purge every
  copy still under your control — memory files, scratchpad files, task/plan artifacts, or
  anywhere else it was written — the moment it's noticed. Tell me it happened and what was
  purged; don't decide on your own whether a rotation is needed, that's my call.

## AWS SSO profiles

- This device has two AWS SSO profiles: **`amplify-admin`** and **`steveadmin`**. Use
  `amplify-admin` for Amplify-specific work; use `steveadmin` for anything else that
  `amplify-admin` can't do (insufficient permissions/scope).
- If unsure which profile a task needs, or a permissions error looks like it might be a
  profile-scope issue, **ask before switching profiles or retrying with the other one**.

## AWS MCP server

- Two AWS MCP servers are installed. **Use `aws-mcp-multi`** for all AWS work — it's the
  proxy that supports switching profiles per call via its `aws_profile` param (values
  `default` → `amplify-admin` SSO role, `steveadmin` → `steveadmin`). The other
  (`plugin:aws-core:aws-mcp`) is single-profile only — don't use it.
- Pass `aws_profile` explicitly on every call, matching the "AWS SSO profiles" guidance
  above for which profile a task needs.

## Releases

- Do **not** bump versions, build packages, create release artifacts, or publish releases
  unless I explicitly ask. Work after a published version is prep for the next version —
  don't pick that version number early.
- Annotated `vX.Y.Z` Git tags are the source of truth for released versions. Tag on
  **`main`**, not `dev`; reset `dev` to `main` only when `git diff main dev` is empty.
- **In a full (end-to-end) release, always run a real review of the release PR before
  merging it** — use the `/code-review` skill on the PR, fix or surface what it finds,
  and only then squash-merge. A quick diff scan is not a review.

## Documentation-first — no guessing

- **Before applying any change**, if you are uncertain about syntax, tool behaviour, config
  format, API semantics, or any other technical detail, **use the Context7 MCP tool to look
  up current documentation first**. Do this proactively — no explicit request needed.
- This applies to libraries, frameworks, SDKs, APIs, CLI tools, config schemas, and
  anything else with external docs. Never rely on training data alone when current docs are
  available through Context7.
- If Context7 returns no result, or the answer is still unclear after searching, **say so
  explicitly** — do not guess. In code, leave a short comment marking the uncertainty (e.g.
  `// TODO: verify — docs unclear on this param`) so it's visible for review.

## How to work

- Keep changes focused; read only the files needed for the task.
- Verify before handoff: a task is done when its focused tests + one normal build pass.
  Prefer focused test runs while developing; avoid repeated build/format loops. For
  docs-only changes, skip builds and verify by reviewing the edited files.
- Prefer concise output and token-saving summaries.
- After using MCP tools or anything else likely to dump a lot of context (large
  file/web reads, big search results, subagent transcripts, etc.), once that phase of
  work is finished, remind me to `/compact`.
